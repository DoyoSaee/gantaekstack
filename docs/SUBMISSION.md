## 1. 문제 — 왜 만들었나

구직 중인 개발자가 실제로 부딪히는 질문은 두 개다.

1. **"내 스택, 아직 팔리는 건가?"** — 이력서의 기술들이 시장 기준으로 현재인지 과거인지 알 길이 없다. 채용공고를 수십 개 읽어봐야 감으로만 안다.
2. **"뭘 배워야 하나?"** — 유튜브와 블로그는 유행을 말하지만, *채용시장이 실제로 요구하는 것*과는 다르다.

기존 서비스는 공고를 "보여주기"만 한다. 공고가 요구하는 기술을 **구조화된 데이터로 바꿔 개인의 이력서와 대조해주는 것**은 없다. 만든 사람 본인이 2026년 프론트엔드 구직자로서 29개 회사에 지원하며 겪은 문제다.

## 2. 해결 — 무엇을 만들었나

**세 개의 축을 같은 기술 어휘로 정규화해 자유롭게 대조한다.**

| 축 | 데이터 | 답하는 질문 |
|---|---|---|
| 시대축 | Stack Overflow 개발자 설문 2017~2025 (ODbL) | "이 기술은 몇 년도에 주류였나" |
| 현재 수요축 | 채용공고 1,800건+ (합법 공개 API 7종 + 직접 수집) | "지금 시장이 뭘 원하나" |
| 개인축 | 이력서 (Gemini 추출) | "나는 뭘 갖고 있나" |

### 화면 4개

1. **이력서 시대 진단(/)** — 이력서/PDF를 넣으면: 스택 추출 → 시대 무게중심("≈2019년") → 직군별 축(프론트/백엔드 분리) → 기술별 진단(정점 연도·추세·후계 기술) → 시장 갭·동반수요 추천 → AI 총평. 결과는 URL·이미지 카드로 공유.
2. **공고 매칭(/match)** — 지원 직전 공고를 붙여넣으면: 요구 스택 × 내 스택 대조(n/m), 공고가 요구하는 스택의 시대(오래된 스택을 쓰는 팀 감지), 문장 속 숨은 요구. **옵트인 기여 시 그 공고가 한국 데이터셋에 익명으로 쌓인다.**
3. **시장 대시보드(/market)** — 요구 기술 TOP 20(지역×직군), 시장이 요구하는 스택의 시대 분포, AI가 포착한 숨은 요구.
4. **스택 직접 입력(/gap)** — 이력서 없이 기술만 골라 격차 확인.

### 차별점

- **"몇 년도 스택" 진단** — 공고 게시 연도가 아니라 *기술 자체의 역사 곡선*으로 시대를 판정. 시장이 요구하는 시대(≈2023년)와 내 시대의 "실질 격차"까지.
- **숨은 요구 추출** — 표면 키워드가 아니라 공고 문장 속 실제 요구("대규모 트래픽 대응", "직접 배포 경험")를 AI가 뽑아 집계.
- **데이터 플라이휠** — 한국 채용 API는 개인에게 닫혀 있다(원티드·워크넷=사업자 인증, 사람인=승인 대기). 크롤링 대신 **유저의 지원 활동 자체가 수집이 되는 구조**(공고 매칭+기여)로 풀었다. 만든 사람이 실제 지원한 공고 21건으로 시작.
- **채점하지 않는다** — 점수·등급 없음. "무게중심 ≈2019년, 다음 걸음은 React"처럼 위치와 방향만.

## 3. AI 활용 — 어떻게 썼나

**LLM을 판정자가 아니라 구조화 계층으로 썼다.**

| 역할 | 모델 | 하는 일 |
|---|---|---|
| 공고 리더 | Gemini 2.5 Flash (structured output) | 공고 원문 → 기술+카테고리+경력+숨은 요구 (1,800건 전수) |
| 이력서 리더 | 〃 | 이력서 → 보유 스택+연차+직군 |
| 총평 작가 | 〃 | 진단 수치 → 사람의 언어 (보이스 가이드 준수) |

**AI가 하지 않는 일**: 시대 무게중심·집계·추천 순위는 전부 결정론적 코드다. 같은 입력이면 항상 같은 결과 — AI가 숫자를 지어낼 수 없는 구조로, 진단의 재현성과 신뢰를 보장한다. (개발 과정 자체도 Claude Code와의 페어로 진행 — AI 네이티브 워크플로)
